# ilist v0.1.8

## Security and data-integrity release

This release closes three issues found during the v0.1.7 review:

- S3-compatible uploads, multipart completion, rename, and move now reject an existing destination instead of overwriting it. Conditional requests also close the race between the initial conflict check and the provider write. Cloudflare R2 copies include its destination-specific conditional header.
- S3 XML responses are read through a bounded stream with a 1 MiB limit. `fast-xml-parser` is upgraded to `5.10.1`, which fixes GHSA-8r6m-32jq-jx6q.
- Share authorization cookies carry the current password-policy revision. Changing or removing a share password increments that revision and immediately rejects authorization cookies issued under the previous policy.

CI now rejects high-severity production dependency advisories and runs the non-visual Playwright suite on every pull request and push to `main`.

## Deployment order

1. Export the remote D1 database outside the repository:

   ```bash
   npx wrangler d1 export ilist-db --remote --output /tmp/ilist-db-before-v0.1.8.sql
   ```

2. Apply all remote D1 migrations before deploying the Worker:

   ```bash
   npx wrangler d1 migrations apply ilist-db --remote
   ```

   This release adds `0017_share_auth_revision.sql`. It adds a non-null `auth_revision` column with a default of `1`; existing share links and password hashes are preserved.

3. Deploy the Worker and Assets together:

   ```bash
   npm run deploy
   ```

4. Smoke-test the deployed application:

   - Authenticate to a password-protected share, change its password as administrator, and verify the old browser authorization is rejected while the new password succeeds.
   - Attempt to upload, rename, and move an S3 item onto an existing file or folder name and verify the operation returns a conflict without modifying either object.
   - Complete one ordinary and one multipart upload on every configured S3-compatible provider.
   - Verify listing still decodes keys containing `&`, quotes, Unicode, and URL-encoded continuation tokens.

## Provider compatibility

AWS S3 and Cloudflare R2 support the conditional operations used by this release. Before production deployment, validate custom S3-compatible providers with the conflict and multipart smoke tests above. A provider that ignores destination conditional headers cannot guarantee protection against a concurrent writer, even though ilist still performs a preflight conflict check.

## Emergency abort and rollback

Keep migration `0017` applied. It is additive and compatible with the v0.1.8 schema; restoring the D1 export is only appropriate when the migration itself failed or data was damaged.

Prefer a fix-forward deployment if v0.1.8 has a critical issue. Rolling the Worker back to v0.1.7 reintroduces the S3 overwrite and share-authorization revocation issues. If an emergency diagnostic rollback is unavoidable, restrict public traffic first and restore v0.1.8 before reopening the service.
